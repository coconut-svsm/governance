# Meeting Minutes: SVSM Development Call (October 14th, 2026)

## Topics:

### TSC Meeting Update

* **Per-CPU Implementation Considered Safe:** The TSC reviewed the safety of the new per-CPU implementation, which replaces the large per-CPU struct with statics collected in a section and copied to each CPU. The review found no Rust safety problems, and the group concluded that requiring `Copy` on the stored types was unnecessary.
* **Deadlock Detection Discussion Continues:** The design of instrumentation for detecting deadlocks and other locking problems remains under discussion. No conclusion was reported.
* **OCP Renamed to OMP:** The proposed Observability and Configuration Protocol has been renamed to Observability and Management Protocol (OMP) to avoid the OCP abbreviation collision with the Open Compute Project.

### Proposed Certify Integrated TPM Command

* **Jeff Presented Direct Attestation of TPM Keys:** Jeff Andersen presented the proposal previously sent to the mailing list, now named `Certify Integrated`. It resembles `CertifyCreation`, but uses an underlying root of trust, such as an SEV-SNP report, instead of a TPM-resident signing key. It would allow callers to obtain platform-backed attestation of a key they create, including its creation data, rather than relying on a preselected endorsement key.
* **Key Leakage and Freshness Motivate the Proposal:** Jeff described customers who want to limit how long they trust keys in case a key leaks. He distinguished freshness of an attestation, established through qualifying data, from evidence about when the key was created. James compared this with existing approaches using ephemeral keys, reset counts, and transparency logs; the group also discussed how much external infrastructure each approach requires.
* **The Role of `outsideInfo` Needs Follow-Up:** The initial discussion assumed that changing `outsideInfo` in `CreatePrimary` would change the derived key. After checking the specification, James said it affects the creation data but is independent of the key derivation function. Nicolai pointed to revision 184, Part 1, section 25.6.3, and Part 3, section 24.1, on primary-object entropy and deterministic creation. Jeff agreed to check this before relying on it as evidence of key freshness.
* **Null-Hierarchy Keys Were Discussed:** Jeff proposed using the null hierarchy so keys would not survive a TPM reset. James noted that a persistent hierarchy seed leaking would remain a problem for keys derived from that seed. The discussion did not establish that the proposed command resolves all of these freshness concerns.
* **Existing Attestation Flows May Offer Alternatives:** Nicolai asked whether SVSM could reuse attestation results already obtained when retrieving storage keys, rather than repeat remote attestation for every TPM key. Jeff said that could suit deployments that trust the storage verifier, while other customers want a fresh hardware report without that storage infrastructure. Nicolai also suggested identifying the response format or platform in the vendor-defined attestation buffer so clients can interpret it.
* **Service Separation and Compatibility Need Design Work:** Jeff proposed having the SVSM kernel bind service-provided attestation data to a service GUID, preventing another service from producing evidence that appears to come from the vTPM. James raised compatibility questions and, after checking the existing specification, noted that the returned manifest structure already contains service GUIDs. The exact relationship between a new service attestation path and the current protocol remains to be worked out.
* **Proposal Will Return to the Mailing List:** Jeff expects the command to reach the TPM library specification in the first half of 2027. James asked him to verify the `outsideInfo`/KDF behavior and repost the proposal to the Coconut mailing list for further discussion. No decision to integrate the command was made.
* **Provisioning Question Raised in Chat:** Arun asked whether the proposal could improve endorsement-key certification while provisioning persistent vTPM state, where an admin CA currently signs the certificate. No specific resolution was recorded.

### TPM-RS Integration Requirements

* **Joe Reviewed SVSM's TPM Requirements:** Joe Richey shared the [TPM-RS repository](https://github.com/tpm-rs/tpm-rs), maintained in a separate organization from TCG, and asked which currently enabled TPM features would be required for a Rust implementation. James emphasized that SVSM uses the reference implementation to provide normal TPM functionality for guest applications, whose requirements may go beyond SVSM's own usage.
* **Most Configuration Choices Were Inherited:** James and Stefano explained that the configuration largely follows the C reference simulator, with simulation and related features disabled and adjustments made to build in SVSM. Features such as Camellia were inherited rather than deliberately selected as requirements.
* **Platform Hooks Were Examined:** Authenticated countdown timers are enabled in the configuration, but participants said the required platform behavior is not wired up. Looking through `libcrt` showed an RDTSC-based time source and entropy support using RDSEED/RDRAND. Joe said TPM-RS aims to work in a `no_std` environment without requiring a custom C library.
* **`CreateLoaded` Is a Potential Compatibility Issue:** Joe said TPM-RS aims to cover roughly the same command set as the C reference implementation while omitting some deprecated commands. He identified the currently enabled `CreateLoaded` command as a possible mismatch, citing security problems with derivation objects that it can create. James noted that he had already objected to its use in a proposed Linux hibernation patch because many deployed TPMs do not support it.
* **Linux Patch Shared for Follow-Up:** James posted [Matthew Garrett's Linux patch proposing use of `CreateLoaded`](https://lore.kernel.org/all/20261008132532.1155166-12-matthewg@nvidia.com/). Joe will discuss the command's problems with Matthew. Joe saw no other major command-coverage conflict in the configuration reviewed during the call.
* **SPDM Is Not Currently Required:** James confirmed that SVSM does not currently support SPDM and uses its attestation protocol for the relevant role. Joe said SPDM could be within TPM-RS's scope.
* **An SVSM Demo Will Follow:** Joe will investigate further and send an SVSM patch demonstrating how to boot with TPM-RS once the implementation is sufficiently functional. Jörg expressed interest, with remaining integration questions to be addressed when a working demo is available.
